Overview & Framework Philosophy

Peregrine is an expressive, header-only C++ web application framework designed to bring the elegance and productivity of modern microframeworks to high-performance native systems programming.

Standard: C++11 Conforming • License: Apache-2.0 • External Dependencies: 0 (OpenSSL optional for HTTPS)

Why Peregrine?

Modern backend web development is dominated by interpreted runtimes (such as Python, Node.js, and Ruby). While these ecosystems offer intuitive APIs, they frequently suffer from memory bloat, high garbage collection pauses, and substantial CPU overhead. Conversely, existing C++ frameworks often impose steep learning curves, require complex build-time code generators (like Protobuf or CMake DTO generators), or link against massive multi-megabyte dependencies (such as Boost).

Peregrine++ is designed for developers who want the simplicity of a modern web framework while retaining the performance, control, and portability of C++.

Fast

Peregrine++ is built in C++ with performance-sensitive applications in mind. It is designed to provide a lightweight HTTP and web application layer without requiring a large runtime environment.

This makes it suitable for applications where resource usage, latency, and execution speed matter.

Lightweight

Peregrine++ follows a header-only architecture, allowing developers to integrate the framework directly into their C++ projects with minimal setup.

There is no separate framework runtime that needs to be installed or managed.

Flexible

Peregrine++ provides building blocks for developing different types of applications, including :

  • REST APIs
  • Web applications
  • IoT gateways
  • Embedded web interfaces
  • Device management systems
  • SCADA applications
  • Industrial monitoring systems
  • Local device configuration portals
  • WebSocket-based real-time applications

The framework is intended to remain flexible rather than being tied to a single application type.

The Peregrine Philosophy

The core idea behind Peregrine++ can be summarized as:

Simple like a lightweight web framework.

Powerful like C++.

Flexible enough for the edge.

Peregrine++ brings web development closer to the systems and devices where C++ is already the natural choice.

Key Technical Differentiators

  • 100% Header-Only Architecture: No pre-compiled libraries or separate linking steps. Simply copy the include/peregrine directory to your project and include <peregrine/peregrine.hpp>.
  • Zero Mandatory External Dependencies: Peregrine uses standard POSIX sockets on Linux, macOS, and BSD, and Winsock2 on Windows. OpenSSL is required only if you explicitly enable HTTPS/TLS.
  • Stateless Cryptographic Sessions: Session state is stored client-side in HMAC-SHA256 signed cookies with automatic key rotation support, requiring zero server-side memory or database locks.
  • Embedded ARM Safety (PIMPL JSON Engine): The internal JSON parser utilizes a strict 4-byte/8-byte pointer representation, completely eliminating GCC ARM AAPCS calling convention warnings (-Wpsabi) on 32-bit embedded Linux.
  • Deterministic Concurrency with Overload Backpressure: Requests are processed by a bounded-queue thread pool. When the server reaches saturation, it immediately sheds load with an HTTP 503 response rather than exhausting system memory.
💡
Production Ready: Peregrine's entire test suite of 52 comprehensive unit tests runs in under 15 milliseconds, validating every routing edge case, multipart boundary slice, session key rotation, and CSRF token permutation.

Quickstart & Hello World

Create, compile, and run your first high-performance native C++ web service with Peregrine in under five minutes.

1. The Minimal Application

Create a new C++ source file named main.cpp and paste the following implementation:

C++11 
#include <iostream>
#include <peregrine/peregrine.hpp>

int main() {
    // 1. Initialize application
    peregrine::App app;

    // 2. Define root endpoint
    app.get("/", [](peregrine::Request& req) {
        return peregrine::Response::text("Hello, World from Peregrine C++!");
    });

    // 3. Define JSON status endpoint
    app.get("/api/health", [](peregrine::Request& req) {
        peregrine::Json doc = peregrine::Json::object();
        doc["status"] = "healthy";
        doc["version"] = "1.0.0";
        doc["concurrency"] = "thread_pool";
        return peregrine::Response::json(doc);
    });

    // 4. Dynamic URL parameter endpoint
    app.get("/greet/<string:name>", [](peregrine::Request& req) {
        std::string username = req.path_params["name"];
        return peregrine::Response::text("Welcome back, " + username + "!");
    });

    // 5. Launch HTTP listener on port 8080
    std::cout << "[Peregrine] Launching server on http://localhost:8080..." << std::endl;
    app.run("0.0.0.0", 8080);

    return 0;
}

2. Compiling the Application

Because Peregrine is 100% header-only, compilation is as straightforward as invoking standard GCC, Clang, or MSVC with -std=c++11 and pointing the include path to include/:

Terminal 
# Linux / macOS (GCC 4.8+ or Clang 3.3+)
g++ -std=c++11 -O2 -I include main.cpp -lssl -lcrypto -lpthread -o my_server
./my_server

# Windows (MinGW-w64 GCC)
g++ -std=c++11 -O2 -I include main.cpp -lws2_32 -lssl -lcrypto -o my_server.exe
.\my_server.exe

# Plain HTTP Only (Zero OpenSSL dependency on Linux)
g++ -std=c++11 -O2 -I include main.cpp -lpthread -o my_server

Request-Response Lifecycle Architecture

An in-depth, end-to-end technical walkthrough of the 11-step execution pipeline from TCP socket acceptance to worker thread wire serialization.

The 11-Step Execution Pipeline

Peregrine employs a deterministic, master-worker concurrency architecture. A single listener thread accepts incoming TCP connections and dispatches tasks into a bounded-queue thread pool. Worker threads execute the full request-response lifecycle independently without shared memory contention.

Detailed Pipeline Breakdown

Pipeline Step Executing Subsystem Technical Description & Failure Modes
1. TCP Accept Listener Thread Main thread blocks on accept(). When a client connects, an operating system file descriptor is allocated.
2. Connection Setup Connection Wraps raw socket fd. If TLS is active, executes SSL_accept() to complete the cryptographic TLS handshake.
3. Enqueue & Shedding ThreadPool Task lambda pushed to bounded queue. If queue capacity (e.g. 64) is reached, server writes HTTP 503 Service Unavailable and drops connection.
4. Worker Dequeue Thread One of N worker threads wakes via std::condition_variable, isolating execution on its private call stack.
5. Timeout Setup Socket Options Applies SO_RCVTIMEO and SO_SNDTIMEO (default: 10 seconds) to mitigate Slowloris denial-of-service attacks.
6. Request Parse detail::parse_request Reads socket stream up to max_body_size. Parses HTTP verb, path, query string, headers, cookies, and multipart files.
7. Session Verification verify_and_load_session Parses session cookie. Verifies HMAC-SHA256 signature against secret_key and secret_key_fallbacks.
8. Pre-Request Hooks before_request Executes global app pre-hooks, verifies CSRF token on mutating methods (POST/PUT/DELETE), then executes blueprint-level pre-hooks.
9. Routing & Views Router::match Evaluates compiled regex patterns. Extracts path parameters. Dispatches route handler or MethodView. Returns 405 if method disallowed.
10. Post-Request Hooks after_request Executes blueprint and global post-hooks. If session.modified is true, computes new HMAC signature. Injects Vary: Cookie.
11. Serialization serialize_response Formats status line, headers, Set-Cookie, and Content-Length. Writes buffer to socket and invokes conn.close_conn().

Memory & Stack Allocation Model

In Peregrine, each request allocates its Request and Response structures entirely on the worker thread's private stack frame. This guarantees that:

  • Zero Cross-Thread False Sharing: No worker threads access or mutate neighboring thread memory.
  • Lock-Free Routing Dispatch: Once initialized during server boot, the Router route table and configuration dictionary are read-only, allowing concurrent reads across all worker threads without a single mutex lock.
  • Predictable Garbage-Free Deallocation: When a request completes, stack unwinding instantly frees all request-scoped allocations without memory fragmentation.
❗
Load Backpressure Guarantee: Unlike unbounded event loops that consume memory until killed by the OS Out-Of-Memory (OOM) killer, Peregrine's bounded task queue enforces hard limits. When under catastrophic load, it maintains latency for admitted requests while politely shedding excess traffic with HTTP 503.

Module 05: PIMPL JSON Engine

Technical specification for peregrine::Json, a lightweight, header-only recursive-descent JSON parser and serializer engineered with a strict 4-byte/8-byte PIMPL(Pointer to IMPLementation) design for 32-bit ARM ABI stability.

Header: <peregrine/json.hpp> • Class: peregrine::Json

Why PIMPL? (The Embedded ARM Calling Convention Problem)

In standard C++ implementations, JSON values holding recursive containers (such as std::vector<Json> and std::map<string, Json>) occupy approximately 72 bytes per instance. When compiling for 32-bit ARM Linux (arm-linux-gnueabihf), the GCC compiler emits AAPCS ABI parameter-passing warnings (-Wpsabi) during vector reallocations.

Peregrine solves this completely by encapsulating its AST node inside std::shared_ptr<Value>. As a result, sizeof(peregrine::Json) is strictly 4 bytes on 32-bit ARM and 8 bytes on 64-bit architectures, guaranteeing complete ABI stability with zero compiler diagnostics.

|                                                                               |
|  Standard By-Value AST:                                                       |
|  sizeof(Json) = ~72 bytes  ---> Triggers GCC ARM AAPCS calling convention    |
|                                 warning (-Wpsabi) on 32-bit Linux embedded!   |
|                                                                               |
|  Peregrine PIMPL Architecture:                                                |
|  sizeof(peregrine::Json) = sizeof(shared_ptr) = 4 bytes (ARM) / 8 bytes (x64) |
|  [ Json Class ] ---> [ std::shared_ptr<Value> ] ---> [ Value AST Heap Node ]   |
|  * 100% ABI compliant across all ARM/MIPS/x86 toolchains with ZERO warnings!  |

Stateless Cryptographic Session Architecture

Instead of maintaining state in server memory or a Redis database, Peregrine serializes session state into a compact JSON payload, encodes it via Base64URL, attaches a Unix epoch timestamp, and signs the payload with HMAC-SHA256: 

token = base64url(json_payload) + "." + timestamp_epoch + "." + base64url(hmac_sha256(effective_key, signing_input))

This delivers instant horizontal scalability across server clusters without sticky sessions or distributed locking.

Module 07: Security & CSRF Defense

Technical specification for Peregrine's multi-layered defense matrix: multi-channel CSRF protection, constant-time XOR token verification, CWE-22 Path Traversal prevention, and Slowloris mitigation.

Header: <peregrine/csrf.hpp> • Namespace: peregrine::csrf

CSRF Verification Engine

Cross-Site Request Forgery is prevented by storing a cryptographic nonce in the signed session cookie and requiring state-modifying requests (POST, PUT, PATCH, DELETE) to prove knowledge of that nonce:

Figure 7.1: Peregrine Multi-Channel CSRF Verification Engine
+-------------------------------------------------------------------------------+
|                      MULTI-VECTOR CSRF VERIFICATION PIPELINE                   |
+-------------------------------------------------------------------------------+
                                        |
  Incoming Request -------------------->| Is method POST, PUT, PATCH, or DELETE?
                                        | (Safe methods GET, HEAD, OPTIONS bypass CSRF)
                                        v
  Exempt Path Check ------------------->| Is path in app.csrf_exempt_paths?
                                        | (e.g. webhooks, public telemetry)
                                        v
  Multi-Channel Extraction ------------>| 1. Form field: req.form_get("csrf_token")
                                        | 2. Header: req.header("X-CSRF-Token")
                                        | 3. Header: req.header("X-CSRFToken")
                                        | 4. Query param: req.arg("csrf_token")
                                        v
  Constant-Time Verification ---------->| constant_time_equal(submitted, session_token)
                                        | Prevents timing-attack byte-leakage!
                                        v
  Verification Failed? ---------------->| Immediately emits HTTP 400 Bad Request
                                        | "CSRF token missing or invalid"

Security Hardening Primitives

  • Timing Attack Defense: constant_time_equal() computes the bitwise XOR across strings in constant time, preventing side-channel byte extraction.
  • CWE-22 Directory Traversal Defense: read_static_file() inspects requested paths, rejecting any containing .. sequences or null bytes ().
  • Slowloris Connection Timeouts: Configures SO_RCVTIMEO and SO_SNDTIMEO socket options to drop lingering half-open connections.
  • Payload Size Enforcement: Pre-allocates buffer size and enforces max_body_size, shedding oversized payloads with HTTP 413.

Feature Recipe: Production RESTful JSON APIs

Step-by-step architectural guide to designing and implementing thread-safe, scalable RESTful microservices with Peregrine, complete with CRUD operations, status code conformance, and validation.

REST Architectural Best Practices in C++

When building microservices in C++, thread safety across worker threads is paramount. All shared database connections, caches, or in-memory repositories must synchronize write access using standard C++11 concurrency primitives (std::mutex and std::lock_guard).

Complete Implementation: Books Microservice

C++11 
#include <iostream>
#include <mutex>
#include <map>
#include <peregrine/peregrine.hpp>

// Domain Model
struct Book {
    int id;
    std::string title;
    std::string author;
    double price;

    peregrine::Json to_json() const {
        peregrine::Json j = peregrine::Json::object();
        j["id"] = id;
        j["title"] = title;
        j["author"] = author;
        j["price"] = price;
        return j;
    }
};

// Thread-Safe Data Store
class BookRepository {
private:
    std::mutex mtx_;
    std::map<int, Book> books_;
    int next_id_ = 1;

public:
    BookRepository() {
        books_[1] = {1, "The C++ Programming Language", "Bjarne Stroustrup", 59.99};
        books_[2] = {2, "Effective Modern C++", "Scott Meyers", 49.95};
        next_id_ = 3;
    }

    peregrine::Json list_all() {
        std::lock_guard<std::mutex> lock(mtx_);
        peregrine::Json arr = peregrine::Json::array();
        for (const auto& kv : books_) {
            arr.push_back(kv.second.to_json());
        }
        return arr;
    }

    bool get(int id, Book& out) {
        std::lock_guard<std::mutex> lock(mtx_);
        auto it = books_.find(id);
        if (it == books_.end()) return false;
        out = it->second;
        return true;
    }

    Book create(const std::string& title, const std::string& author, double price) {
        std::lock_guard<std::mutex> lock(mtx_);
        Book b = {next_id_++, title, author, price};
        books_[b.id] = b;
        return b;
    }

    bool remove(int id) {
        std::lock_guard<std::mutex> lock(mtx_);
        return books_.erase(id) > 0;
    }
};

int main() {
    peregrine::App app;
    BookRepository repo;

    // 1. GET /api/v1/books - List all books
    app.get("/api/v1/books", [&repo](peregrine::Request& req) {
        return peregrine::Response::json(repo.list_all());
    });

    // 2. GET /api/v1/books/<int:id> - Fetch single record
    app.get("/api/v1/books/<int:id>", [&repo](peregrine::Request& req) {
        int id = std::stoi(req.path_params["id"]);
        Book b;
        if (!repo.get(id, b)) {
            peregrine::Json err = peregrine::Json::object();
            err["error"] = "Book not found";
            return peregrine::Response::json(err, 404);
        }
        return peregrine::Response::json(b.to_json());
    });

    // 3. POST /api/v1/books - Create new book
    app.post("/api/v1/books", [&repo](peregrine::Request& req) {
        peregrine::Json payload = req.get_json();
        if (!payload.has("title") || !payload.has("author")) {
            peregrine::Json err = peregrine::Json::object();
            err["error"] = "Missing 'title' or 'author' field";
            return peregrine::Response::json(err, 400);
        }
        Book created = repo.create(
            payload["title"].as_string(),
            payload["author"].as_string(),
            payload["price"].as_number(0.0)
        );
        return peregrine::Response::json(created.to_json(), 201);
    });

    // 4. DELETE /api/v1/books/<int:id> - Remove book
    app.del("/api/v1/books/<int:id>", [&repo](peregrine::Request& req) {
        int id = std::stoi(req.path_params["id"]);
        if (!repo.remove(id)) {
            return peregrine::Response::text("Book not found", 404);
        }
        return peregrine::Response::text("", 204);
    });

    app.run("0.0.0.0", 8080);
    return 0;
}

Feature Recipe: Authentication & RBAC

Implementing end-to-end user authentication, signed session cookies, protected route guards, and role-based access control (RBAC).

Authentication Workflow

  1. Credentials Submission: Client POSTs credentials to /auth/login.
  2. Session Issuance: Upon successful verification, write user identity and role to req.session. Peregrine automatically computes the HMAC signature and attaches the cookie to the HTTP response.
  3. Protected Route Enforcement: Endpoints inspect req.session.has("user") and invoke peregrine::abort(401) or abort(403) if unauthorized.
  4. Zero Server State: Because sessions are cryptographically signed, horizontal scaling requires zero sticky sessions or shared caches.

Complete Authentication & RBAC Example

C++11 
#include <iostream>
#include <peregrine/peregrine.hpp>

int main() {
    peregrine::App app;
    app.secret_key = "session-encryption-key-must-be-kept-secret-32b";
    app.session_cookie_name = "auth_token";
    app.session_lifetime_seconds = 3600; // 1 hour

    // 1. Login Endpoint
    app.post("/auth/login", [](peregrine::Request& req) {
        peregrine::Json body = req.get_json();
        std::string username = body["username"].as_string();
        std::string password = body["password"].as_string();

        // Verify credentials (mock authentication)
        if (username == "admin" && password == "correct-password") {
            req.session["user_id"] = "1";
            req.session["username"] = username;
            req.session["role"] = "administrator";
            req.session.permanent = true;

            peregrine::Json res = peregrine::Json::object();
            res["status"] = "success";
            res["message"] = "Logged in successfully";
            return peregrine::Response::json(res);
        }

        peregrine::Json err = peregrine::Json::object();
        err["error"] = "Invalid credentials";
        return peregrine::Response::json(err, 401);
    });

    // 2. Logout Endpoint
    app.post("/auth/logout", [](peregrine::Request& req) {
        req.session.clear();
        peregrine::Json res = peregrine::Json::object();
        res["status"] = "logged_out";
        return peregrine::Response::json(res);
    });

    // 3. Protected Dashboard
    app.get("/api/dashboard", [](peregrine::Request& req) {
        if (!req.session.has("username")) {
            peregrine::abort(401, "Authentication required");
        }
        peregrine::Json res = peregrine::Json::object();
        res["user"] = req.session["username"];
        res["role"] = req.session["role"];
        return peregrine::Response::json(res);
    });

    // 4. Role-Guarded Admin Endpoint (RBAC)
    app.get("/api/admin/users", [](peregrine::Request& req) {
        if (!req.session.has("username")) {
            peregrine::abort(401, "Authentication required");
        }
        if (req.session.get("role") != "administrator") {
            peregrine::abort(403, "Forbidden: Administrator role required");
        }
        peregrine::Json res = peregrine::Json::object();
        res["admin_action"] = "user_list_granted";
        return peregrine::Response::json(res);
    });

    app.run("0.0.0.0", 8080);
    return 0;
}

Feature Recipe: SPA Frontend Hosting

Host modern Single-Page Applications (React, Vue, Vite, Angular) with zero-configuration HTML5 client-side history fallback and strict backend API isolation.

The SPA Routing Challenge

In single-page applications, client-side routers (like React Router or Vue Router) navigate between pages (e.g. /dashboard/settings) entirely in the browser. However, when a user refreshes the page, the browser requests /dashboard/settings directly from the backend. Traditional static web servers return an HTTP 404.

Peregrine solves this seamlessly via app.serve_spa("dist", "index.html", "api"):

Figure 18.1: SPA Routing Engine and Fallback Decision Tree
+-------------------------------------------------------------------------------+
|                      app.serve_spa() EXECUTION FLOW                           |
+-------------------------------------------------------------------------------+
                                        |
  Incoming Request Path --------------->| 
                                        |
  1. Root Path ("/") ------------------>| Serve dist/index.html (200 OK)
                                        |
  2. Matching Disk File --------------->| File exists in dist/? (e.g. /assets/app.js)
                                        | ---> [YES] ---> Serve file with MIME type!
                                        |
  3. API Prefix Check ----------------->| Starts with api_prefix (e.g. "/api/")?
                                        | ---> [YES] ---> Return JSON 404 (Do NOT serve HTML!)
                                        |
  4. System Probes -------------------->| Starts with "." or ".well-known"?
                                        | ---> [YES] ---> Return Plain 404
                                        |
  5. HTML5 History Fallback ----------->| ANY OTHER ROUTE (e.g. "/dashboard", "/users/42")
                                        | ---> Serve dist/index.html (200 OK)!
                                        | (Allows React/Vue/Angular router to take over!)

Complete Single-Page App Implementation

C++11 
#include <iostream>
#include <peregrine/peregrine.hpp>

int main() {
    peregrine::App app;

    // 1. Dedicated Backend REST APIs
    app.get("/api/user/profile", [](peregrine::Request& req) {
        peregrine::Json res = peregrine::Json::object();
        res["username"] = "alice";
        return peregrine::Response::json(res);
    });

    // 2. Single-Page Application (SPA) Serving
    // Serves static assets from "dist/", falls back unknown non-API routes
    // to "dist/index.html", and isolates "/api/*" from HTML fallbacks.
    app.serve_spa("dist", "index.html", "api");

    std::cout << "[Peregrine] SPA Server running on http://localhost:8080..." << std::endl;
    app.run("0.0.0.0", 8080);
    return 0;
}
